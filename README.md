# spw 双语歌词顺序

[Steam 创意工坊](https://steamcommunity.com/sharedfiles/filedetails/?id=3822500887) · [下载插件](https://github.com/asukua/spw-bilingual-lyrics/releases/latest) · [源码](https://github.com/asukua/spw-bilingual-lyrics) · MIT 开源

这个插件可以调整椒盐音乐桌面版里的双语歌词顺序。想把原文放在上面，还是先看译文，都可以在模组配置里选。

## 安装与使用

1. 使用支持 SPW Workshop API `0.1.0-dev23` 的桌面版椒盐音乐。菜单及歌词刷新接口以 Steam 版 `1.19.0`、当前安装的 `1.19.2` 为验证目标；实际导入与显示仍需在播放器中验证。
2. 打开 **创意工坊 → 模组管理 → 导入模组**，选择 `plugin-io.github.saltlyrics.bilingual-0.1.9.spmod`，然后启用“**spw 双语歌词顺序**”。自行构建的文件位于 `build/libs/`。更新旧版时再次导入同一插件 ID 的新版文件，按播放器提示完成更新。
3. 为新增的歌曲菜单按钮授予播放器提示的“修改应用行为”权限。进入播放页底部的 **…** 菜单，点击 **切换为译文在上** 或 **切换为原文在上**。选择会保存为全局显示顺序，并刷新当前歌词；播放位置与播放状态保持不变。
4. 其他选项仍从该 Mod 的操作菜单进入 **配置** 调整，默认自动识别中文译文、原文在上。在配置页修改后，换到另一首歌再切回来以重新加载歌词；菜单按钮会直接应用顺序切换。

不需要曲库读取权限。歌曲菜单按钮需要 `class-transform`（修改应用行为）权限；未授权或菜单接口不兼容时会提示，保留配置页和原有歌词整理功能。接入时检查实际菜单和刷新签名，不按版本号直接关闭按钮。若正在使用其他提供歌词的 Mod，它们可能竞争同一个加载入口，请先单独验证。

## 支持范围

| 歌词写法 | 处理方式 |
| --- | --- |
| 同一时间戳两行，中文译文有时在前、有时在后 | 按文字特征逐组判断并重新排序 |
| 时间戳独占一行，后面紧接原文、译文 | 将正文绑定到该时间，支持相同的上下顺序设置 |
| `[00:01]原文` 后紧接无时间戳译文 | 关联到上一句，输出同时间戳双行 |
| 同一句中用细空格、制表符、连续空格、带空格的 `/` 或 `\|` 分隔 | 满足中外文判断条件时拆分；可关闭 |
| 同行英文与中文之间只有普通空格 | 仅在片段较长、边界足够明确时尝试拆分 |
| `[00:01][00:05]重复句`、不同小数精度、冒号毫秒 | 按实际时间配对，保留重复位置 |
| 原文与译文都逐字，或只有其中一行逐字 | 共用行开始时间，分别保留两行的逐字时间，不要求字数或行内时间一致 |
| LRC/SPL 显式结束标记、元数据和 offset | 保留已有标记；交换时必要的结束边界处理见下文 |
| 日文中夹有纯汉字句段 | 前后已确认的日中双语组顺序一致时，沿用该顺序 |
| 三行及以上的多语言组 | 保留全部文本及原有顺序，不猜测音译与多种翻译的关系 |

例如，输入：

```lrc
[00:30.96]看这簇微弱火苗悄然在心底边缘生出
[00:30.96]かぼそいひがこころのはしにもる
```

选择“原文在上”后：

```lrc
[00:30.960]かぼそいひがこころのはしにもる
[00:30.960]看这簇微弱火苗悄然在心底边缘生出
```

同一时间戳中谁在前，谁就会成为 SPL 的主歌词。因此“译文在上”时译文会使用播放器的主歌词字号/样式，下方原文使用副歌词样式；这是宿主格式的行为。

自动判断针对“外文原文 + 中文译文”，先去掉逐字时间标记，按完整句子的假名、韩文、汉字及其他字母等文字特征判断，不会将日文中单独的汉字段当成中文译文。纯汉字双行只有在前后均存在已确认的日中双语组、且两侧输入顺序一致时才沿用该顺序；推断出的句子不继续作为其他句子的判断依据。元数据、单语句和三行以上的多语言组会中断这种上下文判断。

插件无法理解句子的真实语义。孤立的纯汉字日文、前后顺序冲突的句段、同语种双行及部分混唱仍可能无法区分，默认保留原顺序。此时可指定“输入第一行为原文/译文”，该选项会覆盖自动判断，适用于输入顺序一致的歌词。混唱误拆时关闭“拆分同一行里的双语歌词”。

`0.1.1` 修复了中文译文夹有英文词组时无法配对的问题。例如 `ロンリーガールはいつまでも 届かない夢見て` 与 `Lonely Girl不管是什么时候 都在做着无法企及的梦`，现在可以按任意上下顺序显示。配对中有明确的日语假名或韩文时，允许另一行中文夹有较长的英文词组；已识别的这类双行不会再因译文内部的空格被拆成第三行。单独一行里的双语拆分仍使用较严格的规则。

`0.1.2` 增加时间戳独占一行的兼容，例如：

```lrc
[00:18.27]
いい事尽くめの夢から覚めた
从满是美好事物的梦中醒来
```

紧接时间戳的首行正文使用该时间，后续连续译文沿用同一时间；同样可以选择原文或译文在上。原来的空时间戳仍保留为上一句的结束边界。空白行、元数据或另一个时间戳会阻止向后绑定，避免把不相干的正文挂到该时间。

`0.1.3` 将模组名称调整为“spw 双语歌词顺序”，简介调整为“调整双语歌词原文译文位置”；保留已有歌词兼容与设置。插件 ID 不变，可更新已安装的旧版。

`0.1.4` 完善独立逐字时间和逐字/逐句混用，增加日文纯汉字句段的上下文判断。例如下面两行可按任意上下顺序显示，各自的行内时间戳仍与原文字对应：

```lrc
[00:30.10]か[00:30.35]細[00:30.62]い[00:30.88]火[00:31.20]が
[00:30.10]纤[00:30.38]细[00:30.66]的[00:30.94]火[00:31.22]焰
```

任意一行也可以使用无逐字标记的整句，例如 `[00:30.10]纤细的火焰`；不需要给另一行补齐字数或逐字时间。方括号与尖括号逐字标记均保留，连续无时间戳译文和独立时间戳后的正文也支持相同处理。

为保留时间含义，含行内逐字时间标记的单句仍不自动拆分。旧版遇到待交换的两行结束时间不同会放弃整份歌词；现在保留各行已有的结束时间，由选为上方的主歌词行决定显示结束时间。若仅原主行有显式结束时间，会把这个已知边界补到新的主行，以免交换后丢失结束边界；不会用最后一个字的开始时间猜测结束时间。若该边界早于新主行的逐字标记，保留这组的输入顺序，其余组继续处理。超长单行、重复时间戳展开后过大的歌词及格式错误的时间戳仍会回退。

`0.1.5` 增加播放页 **…** 菜单里的顺序切换按钮，保存同一个 `output_order` 配置并尝试立即重载当前歌词。它会影响后续歌曲，不是仅对当前歌曲单独设置。保存失败时恢复原配置；关闭“启用歌词整理”后该按钮不可用；停用或卸载插件时移除按钮。刷新失败时会提示切歌后生效。

`0.1.6` 修复 `0.1.5` 仅允许 `1.19.0`、导致 `1.19.2` 跳过菜单加载的问题。以实际接口签名验证替代版本号限制，并在权限不足或接入失败时提示、记录具体错误，不再静默隐藏按钮。

`0.1.7` 修复菜单注册仍会被播放器拒绝的问题：混淆后的菜单构建参数名称为空，无法按 `content` 名称追加。现在在已确认的普通菜单构建方法返回后追加按钮，不依赖参数名称，并将异常同步写入播放器既有日志。

`0.1.8` 曾让所有已识别的双语组显式返回完整歌词来解决切回原顺序的问题，但扩大了普通加载的接管范围，也没有解决配置异步通知导致的刷新丢失；该策略已被 `0.1.9` 的按次刷新机制替代。

`0.1.9` 恢复普通加载的回退规则：显示顺序统一保存，原文、译文身份仍按每首歌的实际文本独立判断，不假定内嵌第一行的身份。仅在点击菜单时，为当前歌曲 ID、当前设置和本次宿主重载创建刷新请求；换歌、后续重载或实际配置变化后失效。内容相同的异步配置通知不再丢弃加载结果。回归测试用内嵌歌词顺序相反的两份 FLAC 标签样本，在同一插件实例中换歌、每首往返切换六轮，并验证逐字标记与音乐文件保持原样。

未实现 QRC、YRC、KRC、TTML、SRT、WebVTT 以及无时间戳纯文本的格式转换。遇到不支持或无法安全解析的内容，返回给播放器原有加载流程，不把它们伪装成已兼容。

## 歌词来源与编码

- 默认内嵌优先，也可选择同名旁挂优先或仅使用某一来源。旁挂文件在音频同目录，按 `.lrc`、`.spl`、`.srt`、`.vtt` 顺序查找；扩展名大小写均可识别。后两种格式目前只会交回播放器。
- 内嵌读取使用 Jaudiotagger 的 `LYRICS` 字段，常见于 MP3 USLT、FLAC/Vorbis 的 LYRICS、MP4 歌词标签；是否能读到取决于容器和标签的实际写法。多个独立歌词字段不自动合并，当前只处理第一个非空值。非标准标签、ID3 SYLT 等不承诺支持。
- 同名旁挂最大 2 MiB；自动编码依次识别 BOM、严格 UTF-8、GB18030。日文旧编码请手动选择 Shift_JIS；自动模式不能可靠区分所有旧编码。内嵌歌词编码由标签读取库处理。
- 当前版本只处理本机文件路径，UNC 网络共享路径交回播放器；常规本地文件链接可以读取。
- 插件不能读取宿主的自定义歌词搜索目录或已经选中的原始歌词。普通加载中，优先来源无法处理或不需改动时交回宿主，不会擅自用次选来源覆盖。菜单发起的当前歌曲重载，会为可识别的双语组提供完整结果，即使目标顺序已与源文件一致；这不会扩大到其他歌曲或后续普通加载。若歌词来源与预期不符，先确认播放器实际使用内嵌还是外部文件，再选择对应来源。

## 构建与验证

需要 **JDK 25**，项目使用官方同版 Workshop API / 打包插件 `0.1.0-dev23` 和带 SHA-256 校验的 Gradle Wrapper `9.8.0`。不需要 Kotlin 编译器或全局安装 Gradle。首次构建需要访问 Maven Central、Google Maven 和 JitPack。

```powershell
$env:JAVA_HOME = '你的 JDK 25 目录'
.\gradlew.bat test plugin
```

输出为 `build/libs/*.spmod`，测试报告为 `build/reports/tests/test/index.html`。包内 `classes/` 包含插件类、PF4J 扩展索引和设置；`lib/` 仅包含独立的 Jaudiotagger，不重复携带宿主 API、PF4J、Kotlin 或 Compose。

单元测试覆盖示例顺序、双行独立逐字时间、逐字/逐句混用、结束边界、日文上下文判断与冲突保留、同句双语拆分、歧义保留、旁挂编码、合成音频标签读取、来源回退、菜单切换的持久化与保存失败回滚，以及反复启停后的旧回调失效。`saltlyrics.hostArchive` 测试属性可额外指定目标播放器 JAR，运行真实 Hook 注册器的目标校验、PF4J 隔离环境发现，以及原生菜单构建、追加项回调和关闭动作。实际通过情况以生成的报告为准；这些检查不代替播放器窗口里的显示及点击验收。

播放器验收建议：分别导入译文在前/在后及同行双语样本，检查两个显示顺序；在歌曲菜单连续切换两次，确认歌词当场刷新且进度、播放/暂停状态不变；在配置页确认顺序已保存；分别用两行逐字、原文逐字/译文逐句、原文逐句/译文逐字检查高亮时间和结束边界；检查夹在日语句中的纯汉字句段；禁用插件确认按钮移除，再启用确认设置保留；拒绝界面权限时确认配置页仍能使用。播放器的副歌词是否逐字高亮仍由宿主决定，插件保留时间标记不代表副歌词一定显示逐字动画。

## 接入依据与维护

采用 `PlaybackExtensionPoint.onBeforeLoadLyrics(MediaItem)`：在 IO 回调中按媒体路径只读取得歌词，返回规范化字符串。无法处理时返回 `null`。配置变更通过不可变快照应用；停用时移除监听器，丢弃跨越停用/配置变更的加载结果。

普通加载使用只返回有改动结果的 `normalize`。菜单重载由宿主当前歌曲 ID 和预期 `generation` 创建请求；只有加载回调的 ID、配置快照和宿主重载代次均匹配时，才使用 `normalizeForPlayback` 对已识别、已经排好顺序的双语组也返回原始文本。请求覆盖同一有效重载代次的回调，不由首个回调消耗，避免被尚未退出的旧任务抢先使用；后续重载或换歌即失效。读取及启动重载使用宿主既有 `lock`，不清空私有缓存、不通过切歌强制刷新。

配置文件保存后，宿主的文件监听会异步再次通知。内容等价的设置保留当前快照身份，避免原本用于丢弃旧设置结果的身份检查误丢弃新歌词；实际内容变化、停用和重新启用仍使旧请求及结果失效。测试以受控的并发通知验证这两类行为。

没有选择 `onAfterLoadLyrics`，因为它只在宿主默认加载失败时执行，无法整理已经存在的内嵌歌词。完整歌词时间轴接口只读，无法写回。歌词转换继续使用公开回调，不 Hook 内部解析器。

早期版本没有采用内部 Hook，因为歌词整理本身不需要承担其兼容成本。新增歌曲菜单操作后，公开 API 仍缺少菜单注册与当前歌词重载入口，因此仅为这两个动作增加结构验证：从目标宿主的 `PlayerMoreMenuFlyout.kt` 特征和实际字节码调用定位菜单，在其中唯一的普通菜单构建方法正常返回后追加原生菜单项，不替换现有菜单；文字转交宿主已有的原生 Composable 绘制，沿用主题与排版，不自行生成 Compose 状态或节点。刷新使用宿主既有 `PlaybackLyricsLoader.reload`，当前歌曲 ID 的读取方法也从该方法的字节码解析，不保存旧歌曲 ID。该方法内部再次校验歌曲 ID，避免切歌竞态。

启动时验证目标唯一性与完整签名，不兼容则只停用菜单增强。`0.1.5` 额外限制版本号为 `1.19.0`，结果屏蔽了接口仍兼容的 `1.19.2`；`0.1.6` 移除这层限制，但只验证 JVM 签名，遗漏了 Hook 注册所需的参数名称。实际宿主解析出的是三个空参数名，`appendContent(..., "content", ...)` 会被拒绝；`0.1.7` 改用参数类型、作用域调用和关闭动作共同定位普通构建方法，测试也扩展到真实注册校验和原生构建执行。没有选择切到下一首再切回的刷新方式，以免扰动播放队列与进度；也不改写播放器安装文件。停用时注销 Hook，旧菜单回调凭启用周期标识失效。实际点击、显示和播放状态保持仍需播放器内验收；未来若出现正式接口，应优先替代这段版本适配。
